Comment le code est vérifié avant d'arriver sur main

Quatre familles de tests, un seul verdict : ./mvnw verify doit être vert, en local puis en CI, avant qu'une PR soit fusionnée. Cette page explique ce que chaque famille vérifie, comment elle le fait, et ce qu'elle a réellement attrapé pendant les sept vagues.

2. Un seul verdict : ./mvnw verify

Maven enchaîne les familles dans un ordre fixe. Le premier échec arrête tout, et c'est voulu : un test unitaire rouge ne vaut pas la peine de démarrer Postgres.

La CI GitHub (.github/workflows/ci.yml) rejoue exactement la même commande dans un job verify, plus un second job contract qui regénère contract/openapi.yaml et échoue si le fichier commité diffère. Deux jobs séparés pour que l'échec du contrat soit lisible (le diff est affiché) sans relancer toute la suite.

4. Les tests d'intégration : jamais de mock de la base

C'est la règle la plus structurante de CLAUDE.md. Chaque endpoint a son *IT, qui démarre l'application complète contre un vrai Postgres éphémère. Rien n'est simulé entre le contrôleur et la table : les migrations Flyway, les triggers, les contraintes CHECK, les REVOKE du rôle psymate_app s'exécutent pour de vrai.

Les ingrédients, module par module

  • Un conteneur par classe de configuration (PostgresTestConfig, ClinicalTestConfig, AuthTestConfig…). Spring met les contextes en cache, donc une dizaine de Postgres au plus par verify, pas un par test.
  • Le principal est posé sur chaque requête avec spring-security-test (authentication(…)) au lieu de rejouer un login : on teste la règle métier, pas la session. Les tests de login, eux, font le vrai parcours (LoginHardeningIT).
  • Une horloge pilotable (MutableClock) pour les règles temporelles : grâce 1 h 15, jeton 24 h, verrou 15 min, sans attendre.
  • Mailpit comme SMTP réel : les tests lisent le mail reçu (destinataire, reply-to, lien de confirmation) via son API.
  • Les événements sont vérifiés dans la table event_publication (outbox Modulith), pas par un mock du publisher.
  • Les tests de rôle : GraceRuleAppRoleIT exécute le service réel connecté en psymate_app, le rôle de production, pour attraper ce que les tests en propriétaire du schéma ne voient pas.
Isolation : le test qui ne manque jamais. Chaque IT d'un endpoint patient contient un cas « praticien B ne voit pas la donnée de A » (403, pas 404), et pour les écrans admin un cas « la réponse ne contient aucun champ de patient ni entry » vérifié sur le JSON brut.

5. Les vérifications d'architecture : qui a le droit de parler à qui

C'est ici que la question des frontières est tranchée mécaniquement. Deux outils, complémentaires, tournent à chaque build.

5.1 Spring Modulith — ModularityTests

Chaque module déclare ses dépendances autorisées dans son package-info.java. ApplicationModules.of(App.class).verify() parcourt le bytecode et refuse toute dépendance non déclarée, et toute dépendance vers une classe interne d'un autre module : seuls les packages marqués @NamedInterface("api") sont visibles.

@ApplicationModule(allowedDependencies = {"identity :: api", "events :: api", "vocabulary :: api", "patients :: api", "shared"})
package com.psymate.clinical;

5.2 ArchUnit — ArchitectureTests

Modulith vérifie les dépendances entre packages. ArchUnit ajoute des règles que Modulith n'exprime pas, écrites en Java sur le bytecode :

RègleCe qu'elle interditPourquoi
noRepositoryAccessAcrossModulesqu'une classe d'un module touche une classe *Repository d'un autre moduleCLAUDE.md : un module ne lit jamais les tables d'un autre ; il passe par la façade
directoryDoesNotTouchClinicalModulestout import de patients, clinical, linking, overview, search depuis directoryl'annuaire public ne doit jamais pouvoir atteindre une donnée patient
identityAdminDoesNotTouchClinicalModulesla même liste depuis identity.adminun administrateur valide des praticiens, jamais des dossiers
reservedPackagesContainNoClassBesidesPackageInfotoute classe dans ai et companionles réserves V2 restent vides (A11)
moduleAdvicesAreOrderedBeforeTheGlobalHandlerun @RestControllerAdvice de module sans @Order(MODULE)sinon le filet global de shared attraperait les erreurs avant les handlers précis
Une règle qui ne peut pas échouer ne vaut rien. Chaque règle est doublée d'un test « négatif » sur un mini-projet factice dans src/test/java/psymatefixture (badarch, badadmin, badmodule, good) : repositoryRuleDetectsCrossModuleAccess prouve que la règle voit bien AService → BRepository, forbiddenDependencyMakesVerifyFail prouve que Modulith refuse bien a → b non déclaré. Si quelqu'un affaiblit une règle, ces tests-là passent au rouge.

7. Le circuit d'une tâche, de l'agent à main

  1. Agent de développement (backend-module-dev) implémente dans son seul module, écrit les *Test et *IT de la tâche, lance spotless:apply puis un premier verify.
  2. Agent reviewer relit git diff main...HEAD sans rien modifier : isolation, frontières, règles CLAUDE.md (Jackson 2, dépendances, secrets), sécurité, qualité des tests. Il classe : bloquant / à corriger / à trancher par l'humain.
  3. Corrections des bloquants et de ce qui est utile ; les décisions produit remontent (règle de grâce 1 h 15, 403 vs 404, publication par pagination…).
  4. Contrat regénéré (make contract), puis verify complet en arrière-plan : vert obligatoire.
  5. PR avec critères cochés un par un, tests ajoutés, dépendances Maven listées, écarts hors module signalés en tête. Un événement done est journalisé dans docs/progress.
  6. CI GitHub rejoue verify + contract sur le head de la PR ; après une fusion voisine, la PR est rebasée et le contrat regénéré avant d'être proposée au merge.
  7. Fusion par vous ; journal merged, archivage de la session, tag de contrat quand le plan le prévoit.

8. Ce que ce filet a réellement attrapé

Quelques prises, par ordre chronologique. Chacune serait passée sans la vérification correspondante.

ModularityTests

reviewer + IT de rôle
M1-03 : la règle de grâce faisait un UPDATE sur entry_version, table que V05 révoque pour psymate_app. Les tests passaient car ils tournaient en propriétaire du schéma. Résultat : GRANT sur trois colonnes + trigger de garde, et GraceRuleAppRoleIT qui exécute le service réel sous le rôle de production.
reviewer
M1-12 : un entier BigInteger (2⁶⁴ + 60) tronqué par longValue() passait la validation « 15–180 » comme un 60.
reviewer
M5-02 : une requête anonyme sur l'annuaire déclenchait un appel façade par profil publié (N+1 non borné). Remplacé par un appel par lot, plafonné à 500.
ContractIT

AdminBootstrapCliIT

reviewer
M1-14b : les filtres admin et e-mail décidaient sur l'URI brute alors que Spring route sur le chemin décodé : /api/%61dmin/… passait sans garde. Corrigé avec un test sur sept chemins encodés.
Ce que le filet ne couvre pas (encore). Les seuils de performance sont mesurés et loggués, jamais assertés (ils dépendent de la machine) ; les tests de timing anti-énumération sont robustes mais sensibles à une machine saturée ; et l'IT ne remplace pas un vrai parcours navigateur, qui viendra avec le frontend.
