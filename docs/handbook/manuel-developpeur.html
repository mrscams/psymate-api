psymate-api · manuel du développeur · état au 1er novembre 2026 (vagues V0 à V8 fusionnées)

Comment ce projet est construit, et ce qu'il faut savoir pour y contribuer

PsyMate est une API de suivi clinique pour psychologues, psychiatres et coachs. Ce manuel explique le flux de travail, l'architecture, la base de données, les événements, la sécurité, les tests et la chaîne CI/CD, avec des extraits de code réels et des schémas. 1. Le produit en une page

Un praticien (psychologue, psychiatre ou coach) tient le dossier de ses patients. Tout ce qu'il note est une entrée : une note, un événement, une situation, un ressenti (émotion + intensité), une séance, un médicament. Chaque entrée appartient à une séance et porte une date d'occurrence avec une précision (jour, mois, année, période, phase de vie). Les entrées se relient entre elles par des liens typés (« déclenche », « précède »…). Une timeline, une recherche plein texte et une vue d'ensemble permettent de relire un dossier. À côté, un annuaire public présente les praticiens vérifiés, et un administrateur valide leurs justificatifs.

Trois règles de fond gouvernent tout le reste (CLAUDE.md) : toute entrée appartient à une séance ; toute correction crée une version (sauf règle de grâce) ; aucune donnée clinique n'est supprimée physiquement (exceptions listées en E9, G Q37) (archivage par archived_at).

Les vagues et les couloirs

D9 découpe le backlog en vagues (V0 → V9). Dans une vague, les tâches tournent en parallèle à condition d'être dans des couloirs différents (un couloir = un module). Deux règles empêchent les conflits : une seule tâche à la fois par module, et une tâche qui touche deux modules (M2-02) tourne seule. À la fusion, chaque PR suivante est rebasée et son contrat regénéré, car toutes regénèrent contract/openapi.yaml.

Les trois agents

backend-module-dev

Implémente une tâche dans un module. Lit CLAUDE.md et les docs cités, écrit code + tests, lance spotless:apply et verify, ouvre la PR, journalise l'avancement.

reviewer

Relit git diff main...HEAD sans rien modifier. Classe en bloquant / à corriger / à trancher. Cherche les fuites d'isolation, les frontières franchies, les règles CLAUDE.md violées, les tests manquants.

seed-perf

Génère les données fictives (patient DEMO, Q22) et mesure les scénarios de performance de A6. Entre en jeu en V9 (M7-01).

Le suivi d'avancement

make log TASK=… AGENT=… STATUS=… SUMMARY="…" écrit un fichier d'événement JSON unique dans docs/progress/events/ (jamais modifié ensuite) et regénère docs/progress/index.html. Deux agents qui terminent au même instant n'entrent jamais en conflit : ils écrivent deux fichiers, et les fichiers fusionnent sans effort entre branches.

3. L'architecture : un monolithe modulaire

Une seule application Spring Boot, un seul déploiement, une seule base, mais découpée en modules Spring Modulith aux frontières vérifiées à chaque build. Chaque module possède ses tables et n'expose aux autres qu'un package api (façades, événements, vues en lecture).

Deux interdits absolus (A5, CLAUDE.md) : directory ne touche jamais une donnée patient ; identity.admin ne dépend d'aucun module clinique. Les deux sont des règles ArchUnit, pas des conventions.

4. Anatomie d'un module

Tous les modules suivent le même plan de packages, un dossier par rôle (G Q33, 2 novembre 2026) : le suffixe d'une classe dit dans quel dossier elle va. Les modules y passent un par un (tâches M9 du plan C8) ; tant que la tâche d'un module n'est pas fusionnée, il garde sa structure actuelle. Voici la cible pour clinical, le plus complet :

com.psymate.clinical
├── package-info.java        @ApplicationModule(allowedDependencies = {...})
├── api/                     @NamedInterface("api") — la SEULE chose visible des autres modules
│   ├── EntryFacade.java         exists, belongsToPatient, patientOf, adjustLinkCount…
│   ├── EntryCreated.java        événements (records, au passé)
│   ├── EntryLinksPort.java      port implémenté par linking (M2-02)
│   └── SessionView.java         vues en lecture
├── controller/              EntryController, SessionController, gestionnaire d'erreurs du module
├── dto/                     EntryDto, CreateEntryRequest (un fichier par DTO, G Q35), EntryMapper (MapStruct)
├── service/                 services @Transactional : EntryService, SessionService, listeners, jobs
├── repository/              EntryRepository (JdbcClient, SQL explicite ; JPA dans les modules CRUD, G Q32)
└── model/                   objets métier : Entry, TimeSpan, GraceRule…

Sens des dépendances : controller → service, dto ; service → repository, model ; model ne dépend que de model et api ; personne ne dépend de controller. Les classes sont publiques entre dossiers d'un même module ; Modulith garde la frontière entre modules, ArchUnit celle entre dossiers.

Déclarer ses dépendances

// src/main/java/com/psymate/clinical/package-info.java
@ApplicationModule(
    allowedDependencies = {"identity :: api", "patients :: api", "vocabulary :: api", "events :: api", "shared"})
package com.psymate.clinical;

import org.springframework.modulith.ApplicationModule;

identity :: api se lit « le package api du module identity, et rien d'autre ». Si une classe de clinical importe com.psymate.identity.auth.LoginService, ModularityTests échoue avec le nom de la classe fautive.

Une façade

Un service

@Service
class EntryService {
  @Transactional
  public Entry create(UUID patientId, CreateEntryCommand cmd) {
    guard.requireOwned(patientId);                       // 403 si pas mon patient
    UUID sessionId = cmd.sessionId() != null ? cmd.sessionId() : sessions.current(patientId);
    checkSession(patientId, sessionId);                  // séance du même patient, type session, non archivée
    Entry entry = repository.insert(patientId, sessionId, cmd);   // entry + entry_version 1 + détail
    links.createForNewEntry(entry.id(), cmd.links());    // M2-02 : même transaction, rollback total
    patients.touchClinicalRev(patientId);
    events.publish(new EntryCreated(...));               // écrit dans l'outbox avant le commit
    return entry;
  }
}

Trois réflexes à retenir : la garde de propriété en première ligne, une transaction par cas d'usage, et l'événement publié dans la transaction (section 8).

5. La vie d'une requête HTTP

Le contrat de l'API

  • JSON camelCase, dates UTC ISO 8601, pagination par curseur (keyset, base64) sauf exceptions documentées (annuaire, recherche : par page).
  • Validation Jakarta sur les DTO, erreurs RFC 9457 application/problem+json avec errors[] = [{field, code, message}].
  • Les DTO sont mappés par MapStruct (généré à la compilation, pas de réflexion).
  • authorType apparaît dans toute réponse d'entrée et est refusé en entrée (422 UNKNOWN_FIELD) : réserve A11 pour le futur compagnon patient.

6. La base de données

PostgreSQL 16 avec les extensions pgvector (réservée à la V2), pg_trgm et unaccent (fonction f_unaccent immuable pour les index). Le schéma est entièrement décrit dans E-modele-donnees.md et créé par Flyway.

Flyway et les numéros réservés

Chaque migration a un numéro réservé à l'avance dans E4, lié à une tâche. On n'édite jamais une migration fusionnée : on en ajoute une.

Les numéros ne sont pas appliqués dans l'ordre chronologique (V10 est arrivé avant V07). Flyway l'accepte sur une base vierge, ce qui est le cas de la CI et de Testcontainers ; en local, make db-reset recrée la base.

Accès aux données : JPA pour le CRUD, JdbcClient pour les projections

Depuis G Q32 (1er novembre 2026), les modules CRUD (patients, vocabulary, directory, identity, clinical.export) passent par Spring Data JPA ; leur SQL natif passe par des fragments *NativeQueries sur l'EntityManager (G Q38). Les projections et requêtes lourdes (search, overview, graphe, timeline, recherche publique de l'annuaire) gardent JdbcClient, décrit ci-dessous. Le projet écrit son SQL. JdbcClient (Spring 7) avec paramètres nommés, jamais de concaténation ; les colonnes jsonb (payload, preferences, details) sont lues et écrites via Jackson 3 (tools.jackson.*). Un index non trivial est documenté dans E et créé par la migration de la tâche qui en a besoin.

// EntryRepository — extrait simplifié
UUID id = jdbc.sql("""

  .param("id", UUID.randomUUID()).param("tenant", tenant).param("patient", patientId)

  .query(UUID.class).single();

Isolation multi-tenant

Chaque table métier porte tenant_id ; chaque patient porte owner_id. La règle d'accès est « mon tenant et mon patient », appliquée par PatientOwnershipGuard avant toute lecture ou écriture, et renvoyant 403 (jamais 404) pour le patient d'un autre.

7. Versions, règle de grâce, append-only

Une entrée est une ligne entry (identité, dates, statut) qui pointe vers sa version courante dans entry_version (titre, texte, payload). Corriger = insérer une nouvelle version et déplacer le pointeur. L'historique complet reste lisible via GET /api/entries/{id}/versions.

Pourquoi un trigger en plus du code ? Parce que entry_version est en REVOKE UPDATE pour le rôle applicatif. La grâce a besoin d'un UPDATE : plutôt que de rendre toute la table modifiable, on autorise trois colonnes (GRANT UPDATE (title, body, payload)) et un trigger refuse tout ce qui n'est pas « version 1, pas de v2, pas de lien, moins de 2 h ». Ce point a été découvert en revue de M1-03 : les tests tournaient en propriétaire du schéma et ne voyaient pas le refus. D'où GraceRuleAppRoleIT, qui exécute le service réel sous psymate_app.

8. Événements et outbox

Les modules ne s'appellent pas en cascade : ils publient des événements que d'autres consomment. Spring Modulith enregistre chaque publication dans la table event_publication dans la même transaction que la donnée métier (pattern transactional outbox), puis livre les abonnés après le commit.

// Un abonné, côté clinical : idempotent et indépendant du praticien courant
@Component
class IntakeSessionListener {
  @ApplicationModuleListener
  void on(PatientCreated event) {
    jdbc.sql("select pg_advisory_xact_lock(hashtext(:k))").param("k", event.patientId()).query().listOfRows();
    if (repository.intakeExists(event.patientId())) return;     // déjà fait : rejeu sans effet
    repository.insertIntakeSession(event.tenantId(), event.patientId(), event.ownerId());
  }
}

Les événements V1 : PractitionerRegistered, …Approved, …Rejected, …Suspended, VerificationSubmitted, PreferencesChanged, PatientCreated/Updated/Archived, EntryCreated/Corrected/Archived, LinkAccepted/Rejected, ProfilePublished/Unpublished. Ils ne transportent jamais de texte clinique : des identifiants et des codes.

9. Sécurité : sessions, filtres, rôles

Pas de JWT : une session serveur (Spring Session JDBC, table spring_session) avec un cookie HttpOnly / Secure / SameSite=Lax, 12 h d'inactivité ou 30 jours avec « rester connecté » (Q6). CSRF désactivé parce que l'API n'accepte que du JSON et que le cookie n'est pas envoyé inter-sites.

Ce qu'il faut savoir du compte praticien

  • États (A10.3) : email_pending → docs_pending → under_review → approved | needs_more | rejected ; plus suspended/closed. Le login répond 403 EMAIL_NOT_CONFIRMED ou ACCOUNT_SUSPENDED selon l'état, mais seulement après un mot de passe correct (anti-énumération).
  • Mots de passe : Argon2id, ≥ 12 caractères, liste locale de 10 000 mots de passe courants (pas d'appel externe). Verrou : 5 échecs email+IP → 423 pendant 15 min, persisté dans locked_until.
  • 2FA TOTP (RFC 6238, Java standard, secret chiffré AES-GCM avec app.crypto.key), codes de secours hachés à usage unique, obligatoire pour accéder à /api/admin/**.
  • Justificatifs chiffrés AES-256-GCM sur disque, servis par URL signée HMAC 5 min, chaque lecture journalisée dans document_access_log (append-only).
  • Journal : tout est dans security_event (login_ok, 2fa_enabled, admin.decision, patient.read…), lu via la vue admin_journal_v (Q29).

10. Erreurs et contrat OpenAPI

Une seule forme d'erreur

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{ "type": "about:blank", "title": "Validation échouée", "status": 422,
  "detail": "Certains champs sont invalides.", "instance": "/api/patients/…/entries",
  "code": "VALIDATION_FAILED",
  "errors": [ { "field": "feeling.intensity", "code": "OUT_OF_RANGE", "message": "L'intensité doit être comprise entre 0 et 10." },
              { "field": "feeling.emotionCode", "code": "UNKNOWN_EMOTION", "message": "Cette émotion n'existe pas dans votre catalogue." } ] }

Le builder et les codes vivent dans shared (M7-02). Chaque module garde son @RestControllerAdvice avec @Order(AdviceOrder.MODULE) pour ses exceptions métier ; le filet global de shared attrape le reste (JSON malformé, 404, 405, 415, 500). Les textes viennent de messages_fr.properties (messages_en si disponible), jamais en dur.

Le contrat est généré, jamais écrit

springdoc lit les contrôleurs et produit contract/openapi.yaml (clés triées, diff lisible). Le fichier est commité ; ContractIT échoue si le fichier commité diffère de ce que l'application génère. Les operationId sont les noms de méthode des contrôleurs : uniques dans tout le projet (createPatient, getTimeline, searchPublicDirectory…), sinon springdoc les renumérote et casse les clients générés.

11. Les tests

Le détail est dans la page Filet de tests PsyMate. L'essentiel :

Unitaires *Test (28)

Domaine pur, tables de cas : grâce, précisions temporelles, matrice de liens, TOTP, parsing de recherche.

Intégration *IT (54+)

Spring Boot complet + Postgres réel (Testcontainers pgvector/pgvector:pg16, Mailpit), MockMvc, principal posé par spring-security-test, assertions SQL. Jamais de mock de la base.

Architecture

ModularityTests (Modulith verify()) + ArchitectureTests (ArchUnit) ; chaque règle prouvée par un contre-exemple dans psymatefixture.

Transverses

FlywayMigrationIT (schéma attendu, REVOKE), ContractIT, ReservesConformanceIT (réserves V2 et compagnon).

Trois habitudes à prendre : chaque endpoint a un cas « praticien B → 403 » ; chaque règle temporelle utilise un Clock injecté ; chaque événement attendu est vérifié dans event_publication.

14. L'arbre des connaissances

Ce qu'il faut maîtriser pour travailler ici, et dans quel ordre. Chaque branche s'appuie sur celle d'en dessous ; les feuilles sont ce que vous manipulez chaque jour.

Parcours conseillé (deux semaines)

  1. Jour 1–2 : le domaine. Lire docs/00-contexte.md, A1 (langage), A2 (cas d'usage), B2–B4 (écrans), G (décisions). Objectif : savoir dire ce qu'est une entrée, une séance, un lien, une version, sans regarder le code.
  2. Jour 3 : le modèle de données. E3 table par table, E4 (migrations), E7 (options tranchées). Ouvrir V01__init.sql et V05__clinical.sql à côté : vous devez reconnaître chaque colonne.
  3. Jour 4 : lancer et toucher. make up, ./mvnw spring-boot:run, make admin, puis s'inscrire, créer un patient et une entrée via contract/openapi.yaml et un client HTTP. Regarder les lignes apparaître dans entry, entry_version, event_publication.
  4. Jour 5 : Spring Modulith. Lire chaque package-info.java, puis faire volontairement une dépendance interdite et lancer ModularityTests : voir le message. Lire ArchitectureTests et ses fixtures.
  5. Jour 6–7 : un module de bout en bout. patients est le plus lisible : PatientController → PatientService → PatientRepository → PatientIT. Puis clinical pour les versions et la grâce (GraceRule, GraceRuleAppRoleIT, trigger V05).
  6. Jour 8 : événements. events (publisher, republication, EventDeduplicator), un abonné (IntakeSessionListener), un test qui lit event_publication.
  7. Jour 9 : sécurité. SecurityConfig, les trois filtres, LoginService, LoginHardeningIT, TotpIT. Comprendre pourquoi le statut du compte n'est révélé qu'après le mot de passe.
  8. Jour 10 : tests et CI. Lancer un seul IT (./mvnw -Dit.test=PatientIT -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false verify), lire ci.yml, ContractIT, le Makefile.
  9. Semaine 2 : une vraie tâche. Prendre une tâche du runbook F (section 16), la faire comme un agent la ferait, demander la revue, obtenir un verify vert, ouvrir la PR.

16. Votre première tâche : la checklist

  1. Lire CLAUDE.md en entier. C'est court, et chaque ligne est une règle vérifiée par le build ou par la revue.
  2. Prendre le texte de la tâche dans docs/F-runbook-agents-backend.md et lire tous les documents qu'il cite, dans l'ordre.
  3. Créer un worktree : git worktree add .claude/worktrees/<ID> -b worktree-<ID> main. Travailler uniquement dedans, uniquement dans le module indiqué.
  4. Commencer par la migration si la tâche en a une (numéro réservé en E4), puis expected-schema-v01.yaml, puis le domaine, le service, le repository, le contrôleur, et les tests en même temps que le code.
  5. Écrire les tests que la tâche nomme, plus le cas « praticien B → 403 », plus l'événement dans event_publication si la tâche en publie un.
  6. ./mvnw spotless:apply, make contract, puis ./mvnw verify : vert. Si un test d'architecture est rouge, la solution est une façade dans le package api du module qui possède la donnée, jamais une exception à la règle.
  7. PR avec le template : ID de tâche, critères cochés un par un, tests ajoutés, dépendances Maven ajoutées (normalement aucune), écarts hors module signalés en tête. make log TASK=… STATUS=done et commiter l'événement.
  8. Après fusion d'une PR voisine : rebaser, regénérer le contrat, relancer verify. Après la vôtre : make log … STATUS=merged, supprimer le worktree.
Si vous ne retenez que trois choses. (1) Le module ne parle aux autres que par leur package api et par des événements. (2) Rien n'est supprimé, tout est versionné, et c'est Postgres qui le garantit. (3) ./mvnw verify vert avant toute PR, sans jamais désactiver un test ni une règle.
